### A. Cross-story seams — invisible to every per-story review, visible only in the whole-epic diff

**A1. `runPrediction` has no staleness guard, though Story 1.3 built exactly that guard for the neighbouring path.**
`src/pages/PredictPage.tsx:311-372` sets `setResult(prediction)` unconditionally when the
request resolves. Story 1.3's external review found and patched the same class of race on the
preload path, and the fix is right beside it: a `seriesLoadSeq.current` counter bumped by the
reset effect at `:100-111`. Two rapid method switches can land the slower response last, so the
card shows one method's probabilities under another method's label. Nothing in the suite or the
matrix covers it: Story 1.4 pins method-switching *state preservation*, and the matrix drove
two methods sequentially.
*Disposition: fix now (proposed — awaiting human application).* Small patch mirroring the
existing pattern, plus a case in `predict-flow-regression.test.tsx`.
*What would prevent the next one:* see B5 — this is what a whole-epic diff review catches that
five story-scoped reviews did not.

**A2. The contact `startedAt` pair can lock the form permanently, with copy that tells you to repeat the failing action.**
`src/pages/HomePage.tsx:36` initialises `contactStartedAt` once per page load (lazy
`useState`); `:154` re-stamps it **only after a success**. `supabase/functions/handle-contact/index.ts:10`
rejects anything older than `MAX_SUBMISSION_AGE_MS` (24 h) with the generic line at `:60`,
"Verification failed. Please try submitting the form again." A tab opened yesterday can never
submit until it is reloaded, and the instruction is the thing that fails again. Both halves
were written by Epic 1's contact hardening (`b8b20dc`), and no test or matrix cell exercises the
age rule — §2's Contact cell is `[!]` for an unrelated reason (F10).
*Disposition: defer, split 2026-09-29 (Q3 discussion) — client half → **Story 3.3**, server half
→ **Story 3.2**.* 3.3 (`3-3-contact-form-feedback-fr-17-issue-2-phase-3`) owns the form's states
and should re-stamp `startedAt` on an age rejection. The server half — distinct copy for
too-old vs too-young — must ride **3.2**, because 3.2's AC explicitly freezes "honeypot + timing
checks + validation unchanged"; after that story the behaviour is pinned and 3.3 could only
change it by reopening 3.2.

**A3. Story 1.5's shared-harness retarget silently moved Story 1.4's series-path coverage off the card.**
`src/pages/__tests__/helpers.tsx:128-130`'s `submitPrediction()` now clicks
