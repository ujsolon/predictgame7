# PRD Quality Review — Predict Game 7

*Rubric: `.qoder/skills/bmad-prd/assets/prd-validation-checklist.md`. Inputs reviewed: `prd.md`, `addendum.md`, plus the four `reconcile-*.md` passes in this workspace and spot-checks against the live repo. Context: reverse-engineered baseline for a live solo-built app; primary job is triaging issues #2–#6 against requirement status; launch-tier-but-gated; terse solo owner on the fast path.*

## Overall verdict

This is a genuinely good PRD: the [LIVE]/[PLANNED]/[PLANNED-GATED] taxonomy, the every-FR-has-consequences discipline, and the honest gating logic make it fit for its triage job, and almost none of it reads like template furniture. What's at risk is narrower than "is this PRD good": one leg of the vision ("shareable") is measured by SM-3 and lived by UJ-1 but owned by no FR; Q-4 is labeled "non-blocking" in §11 while §8.1 commits FR-21 — the release item whose feasibility Q-4 itself says it determines; and several [LIVE] baseline claims (FR-24's "auth events", the 4-step funnel "reportable today", FR-23's "ephemeral" premise, FR-4's catalog gating) assert runtime behavior the reconciliation passes couldn't verify against the repo. None of these blocks the gate posture; all should be resolved before this feeds epics or architecture.

## Decision-readiness — strong

The status taxonomy is a decision instrument, not decoration: `FR-8 **[LIVE — quality target; issue #3 pending]**` admits that a LIVE label and a shipped reality diverge, and says so in the header. Addendum §E is exactly the artifact the triage job needs — every open issue has a row, a target FR, and a "triage read". Trade-offs name what was given up: SM-1 discloses the gate's construction ("≈3× the ~500 conservative research floor and well under the ~2–3k realistic band — deliberately beatable") and the below-gate branch ("reposition as portfolio/demo; monetization plans scrapped"). Resolved questions are struck through with dates and decisions (Q-3, Q-6, Q-7), so nothing reads as smoothed-to-neutral. A pusher would find their objections acknowledged, not dodged. No findings beyond what other dimensions surface.

## Substance over theater — strong

The vision is earned and non-swappable: the post-538-collapse positioning bet is traceable to sourced research (addendum D, NYT link) rather than written to fill a section. NFRs are product-specific to an unusual degree — NFR-D2 exists because "README's stale '0.2.0' is the cautionary case" (I verified: README line 136 says `0.2.0`, package.json says `0.2.2`), NFR-V1 exists because the vendor "may be deprecated entirely if the project plateaus as a demo". NFR-P1 pre-empts the boilerplate critique itself: "recorded at owner's direction as a target created without benchmark basis". Three UJs, each named, each picked up by "Realizes UJ-x" tags on FR-1/2/3/5/6/8/10/12/14/15 — no persona furniture. The "Builder JTBD" line ("if the audience doesn't materialize, that outcome has standalone value") is anti-theater: it states the honest reason the project survives a gate failure. No findings.

## Strategic coherence — adequate

The thesis — open, explainable Game 7 models as an unclaimed niche, proven in the 2027 playoff window — is stated, dated, and drives §8.1 almost line by line ("This section defines the next major release, whose sole purpose is to make the Traffic Gate test (SM-1) valid"). Counter-metrics exist and are real (SM-C1 "SEO padding", SM-C2 "vanity"). SM-2/3/4 validate the thesis rather than count activity. But the coherence breaks on one specific leg: §1 promises "a searchable, explainable, **shareable** analytics experience"; UJ-1's resolution is Dana "shares the result back into the chat"; SM-3 targets ">5% share-driven visits"; addendum D names the lever — "per-matchup shareable prediction pages published *before* a series reaches 2-2 so they index during the spike". No FR converts that lever into a requirement. §7 reduces sharing to "sharing means screenshots/links", and FR-1's deep-links are Home-originated navigations, not user-generated result URLs — nothing owns a URL that encodes *Dana's* prediction. SM-3 and the UJ-1 loop measure a capability the feature set doesn't commit to.

### Findings
- **[high]** "Shareable" vision leg has no owning FR (§1, §2.3 UJ-1, §9 SM-3, addendum D vs §4/§7) — the PRD's first-paragraph promise and its second success metric both depend on share/result deep-link capability that exists only as a measured accident; an agent triaging a "shareable result link" request would find no FR to map it to, and the addendum's identified SEO lever stays unowned. *Fix:* add a [PLANNED] FR for shareable result URLs (or explicitly record in addendum G that screenshots + featured-card deep-links are the judged-sufficient sharing mechanism and SM-3 measures those), so the vision, SM-3, and §4 agree.

## Done-ness clarity — adequate

The backbone is solid: nearly every FR carries "Consequences (testable)" bullets, and the good ones are sharp — FR-5 "Probabilities for the two teams sum to 100% (±rounding)", FR-25 "produces these numbers for Apr–Jun 2027 without ad-hoc surgery", FR-18 "automated search finds zero mojibake/encoding artifacts in shipped strings", FR-30's explicit QA matrix. Bounds beat adjectives in NFR-U1 ("no other surface is exempt by omission"). But this is the dimension downstream story creation leans on hardest, and there the soft spots matter:

### Findings
- **[medium]** Multi-method comparison — a core-loop differentiator — has no testable consequence (§4.1 FR-4/FR-5 vs §2.3 UJ-2) — UJ-2's climax is "sees how different methods disagree", and README calls "Compare multiple prediction methods" a headline claim, but FR-4's consequences only test catalog activity and non-breaking switching, and FR-5's output is singular. If comparison today is sequential re-runs, UJ-2 overstates; if it's a side-by-side view, no FR ships it and a refactor could delete it while "passing" FR review. *Fix:* one consequence on FR-4 or FR-5 stating exactly what a multi-method result renders as today.
- **[medium]** FR-3's validation boundary is undefined (§4.1 FR-3) — "Invalid/missing scores produce inline validation" never says what counts as invalid for a Game 7 predictor: is a score set where one team already reached 4 wins through Game 6 legal input? The archive only contains real Game 7s (3–3 after six), but Custom Matchup invites invented sequences. This edge is a story-creation blocker on the product's own "counterfactuals" JTBD. *Fix:* one clause defining whether clinched standings are rejected, accepted-as-hypothetical, or predicted-anyway.
- **[medium]** FR-2/FR-21 acceptance is unwritable without the `series.status` domain (§4.1 FR-2 "reflect the latest data pipeline update", §4.4 FR-21 "reflect latest results") — status is the discriminating mechanism for glossary-level terms ("Active Series") and pipeline semantics ("initialize and finalize"), yet neither PRD nor addendum §B enumerates its values or the active-vs-historical rule. As written, the pipeline FRs' "testable" consequences can't be turned into tests. *Fix:* addendum §B line enumerating `series.status` values and the discrimination rule, flagged as a required input to pipeline design (reconcile-data-model Gap 4 already prescribes this; it hasn't been executed).
- **[low]** Gated FRs carry placeholders in "Consequences (testable)" headers (§4.1 FR-9, §4.5 FR-22, §4.2 FR-13) — FR-9 and FR-22's consequence sections say "pending discovery — Q-1" and FR-13's "missing video degrades cleanly" is adjectival. This is honest and consistent with [PLANNED-GATED] status, so it's not a defect — but it does mean "every FR has a testable consequence" holds with three exceptions, and those exceptions should be visible at a glance, not discoverable per-FRD. *Fix:* a one-line note at §4 head: gated FRs' consequences are placeholders by design until their discovery items land.

## Scope honesty — strong

This is where the PRD is most disciplined: §7's non-goals each carry a reason and one even back-bonds the journeys ("this also bounds §2.3: no 'during-live-game mobile' journey exists"); `[NON-GOAL for MVP]` appears exactly where it does work (FR-13); `[NOTE FOR PM]` callouts sit at real tensions (FR-30's "a test framework alone won't close this — budget for manual QA passes"); de-scoping in §8.2 states cost logic ("heavy content-ops cost with uncertain SEO payoff"). Open-items density — 6 live Qs, 4 assumptions — is appropriate for a gated launch where §8.1's scope is decidable today. Two blemishes keep it from spotless.

### Findings
- **[high]** Q-4 is tagged "non-blocking" while it gates a §8.1 release item (§10 Q-4, §11 "Still open (non-blocking…)", §8.1) — Q-4's own text says the active-series data source "determines feasibility of FR-21 automation", and §8.1 commits "Data pipeline automation, both modes (FR-20/21) so Active Series are live-current without manual work". If no usable free-tier data source exists, the release promise fails mid-window and the SM-1 test itself is compromised (§1 calls "an automated active-series data pipeline" a near-term priority). Calling this non-blocking smooths the PRD's single largest execution risk. *Fix:* relabel Q-4 as blocking-for-FR-21-in-release with a decision-by date before the 2027 offseason pipeline run, and name the fallback (accept §4.4's manual status quo for one more window) in §8.1/§8.2.
- **[medium]** Several [LIVE] baseline claims are runtime assertions the workspace's own reconciliation passes could not verify (§4.6 FR-24, §4.5 FR-23, §4.1 FR-4, §5 NFR-S2) — FR-24 claims "auth events" emit to PostHog (reconcile-posthog A-4 found only identify/reset wiring, no named event) and a 4-step funnel "reportable today" (A-3: the shipped funnel is 3-step; Detailed Analysis is a companion insight); FR-23's "Anonymous Visitors' runs stay ephemeral" conflicts with `predictions` being described as "active storage" with no confirmed write-path (reconcile-data-model Gap 1 — if rows are being written today, NFR-S2's "no PII collected beyond contact submissions" also needs re-examination); FR-4's `is_active` gating may be design intent rather than observed behavior (Gap 3). For a reverse-engineered baseline, an unverified [LIVE] is worse than an honest [LIVE-unverified]: the PRD's whole purpose is deciding "new vs. change" against these statuses. *Fix:* run the code inspections the reconcile passes call for (they list exact files), then confirm or downgrade each claim; add `[ASSUMPTION:]` tags where verification can't be done now so they're indexed.

## Downstream usability — adequate

The glossary is real and mostly load-bearing — "Traffic Gate", "Betting-Adjacent Output", "Anonymous Visitor" are defined once and used consistently, and cross-refs resolve (FR-9→FR-22, glossary→FR-20/21, Q-refs all land). UJs have named protagonists with inline context. §0's stated audience includes "AI/agent workflows (epics, architecture, build)", so this PRD is chain-top, which raises the bar. Two gaps:

### Findings
- **[medium]** The NFR-V1/FR-25 refactor baseline — the instrumented event inventory — exists only in an external report (§4.6 FR-24, §5 NFR-V1, addendum §A) — the PRD defers depth to the addendum, and the addendum defers further ("10 instrumented events") without naming a single event. NFR-V1's decoupling pass must "preserve event names through the swap", FR-25's API/MCP retrievability is only testable against named events, and SM-1's "total predictions made" has no declared source-of-truth event (reconcile-posthog A-1, rated HIGH, disposition still unexecuted). An architecture agent extracting from this PRD would have to re-derive the registry from `posthog-setup-report.md`. *Fix:* fold the 10-event table into addendum §A and mark the SM-1/SM-2 conversion event explicitly.
- **[low]** Addendum §E's triage map omits an issue→FR link the PRD body asserts (§4.1 FR-4 vs addendum §E) — FR-4 tags method-switching consistency as "issue #3 target", but §E's row for #3 maps only to "FR-8, FR-30, NFR-R2/U1". Since §E *is* the PRD's primary triage artifact, an incomplete row means closing #3 without touching FR-4 would pass the map. *Fix:* add FR-4 to #3's "Maps to" cell.

## Shape fit — strong

The PRD knows what it is: §0 declares itself a "stable baseline... used to triage GitHub issues (#2–#6)" and puts source depth in the addendum — the right split for a brownfield reconstruction for a solo builder. The status taxonomy is precisely the shape a reverse-engineered baseline needs. UJ density is right for a consumer-facing web app owned by one builder (three journeys, plus the owner-side SM-4 ops signal). Brownfield references I spot-checked are accurate: `src/pages/SamplePage.tsx` exists (Q-8), `src/main.tsx` carries the PostHog provider as addendum §A claims, the `keepalive` workflow exists in `.github/workflows/`, and `supabase/scripts/load-games/main.py` — the "precedent pattern for FR-20/21" — is real. The one brownfield hazard (unverified [LIVE] runtime claims) is already captured under Scope honesty rather than a shape problem. No further findings.
